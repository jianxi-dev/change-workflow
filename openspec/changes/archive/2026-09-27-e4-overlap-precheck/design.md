## Context

当前 CW 的 G1 实施 gate 在「第 0 步·建票级分支」之前没有 overlap 预检。两个并行 change 改同一文件时，当前机制无法阻止冲突——只有 merge 时才发现。

软件工厂的 `new-feature` 开工前 `gh pr list` + 查未提交工作，有重叠就停而报告。本设计将同样的模式应用到 CW 的 G1 实施 gate。

**约束**：
- 纯 `gh` 命令，无新脚本、无新依赖
- 不改变 G0-G4 流程语义——只在 G1 开工前加一道预检
- 文件级重叠判定（同一文件即重叠），不做行级判定

## Goals / Non-Goals

**Goals:**
- G1 开工前扫描 open PR 改动文件，与待改文件交集非空即停
- 停而报告冲突 PR 编号 + 文件列表
- 纯文档规则，无新脚本

**Non-Goals:**
- 不做行级重叠判定（同一文件不同区域不算冲突）
- 不自动解决冲突（只停报，不自动 rebase/merge）
- 不改变现有 Blocked by 机制（两者互补）

## Decisions

### 决策 1：放在 SKILL.md G1 实施 gate 开头

**选择**：在 `SKILL.md` 的 G1 实施 gate「第 0 步·建票级分支」之前加「第 0 步·overlap 预检」。

**理由**：
- 纯文档规则，不需要新脚本
- 与现有 G1  gate 结构一致（第 0 步 → 第 0.5 步 → ...）
- 消费仓升级自动获得

**备选**：独立脚本 `scripts/cw-overlap-check.sh` — 拒绝，纯 gh 命令足够，不需要新脚本。

### 决策 2：文件级重叠判定

**选择**：以文件路径为粒度，同一文件即重叠。

**理由**：
- 文件级简单、确定性强
- 行级判定需要 diff 分析，复杂且可能误报
- 文件级已经能覆盖大多数冲突场景

**备选**：行级判定 — 拒绝，过度设计。

### 决策 3：停报而非自动解决

**选择**：发现重叠时停而报告，不自动 rebase/merge。

**理由**：
- 自动解决可能引入新问题（rebase 冲突、语义冲突）
- 停报让人决策，符合「唯一人工介入 = risk-medium/high PR 合并确认」原则
- 等冲突 PR 合并后再开工是最安全的策略

## Risks / Trade-offs

- **[文件级误报]** → 两个 PR 改同一文件不同区域时会被拦下，但这是安全侧的代价（宁可误报也不漏报）
- **[open PR 不全]** → `gh pr list` 只扫 GitHub open PR，本地未 push 的分支不在范围内（可接受，因为冲突主要发生在 PR 层面）
- **[与 Blocked by 重复]** → Blocked by 是声明式依赖（DAG），overlap 是运行时冲突检测，两者互补不重复
