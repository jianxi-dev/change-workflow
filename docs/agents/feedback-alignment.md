# 反馈对齐与输入规范

> 用户（维护者）反馈 → agent 实现 之间的对称确认协议。目的：拆票前消灭「静默误读」，交付后消灭「静默丢弃」。配套：[缺陷流程](./defect-workflow.md)、[UI 反馈四要素](./ui-feedback.md)、[质量门禁](./quality-gates.md)（QG-10、DQ-9）。
> 2026-11-18 经维护者裁定生效：①对账表强制；②禁止静默丢弃；③回复约定「全按默认 + 指定改哪条」。
> 2026-11-22 扩展：新需求/优化线在 G0-PRE 1a 同样强制对账（触发信号与豁免见 §二），`cw-tickets-check.sh` C11 机检 spec issue 的 `## 输入对账` 段。
> 2026-11-26 补充：开发后反向对账（§九「交付对账表」）——逐条写清这一步实际新增/调整/优化了什么功能点，供用户按功能点实测。

## 一、为什么（实证）

editor-surface-batch21：20 票交付，8 票被重开（首验通过率 60%）；加 doc-property-refine 2 票、batch20 1 票、既有 2 票，共 13 张重做 + 1 张待真机（#903）。按主因：

| 主因 | 票 | 一句话机制 |
|---|---|---|
| 需求语义误读 | #1044 #1049 #1054 #1055 #1050(徽标) | 双控件/单面板、工具条时机、复用语义、图标 vs 文字、标识设计 |
| 验收口径错 | #1053 #1057 | 断言测代理属性（text-overflow / sticky），可见真相来自另一属性 |
| 面×状态覆盖缺失 | #1051 #1056 #1016 #1050(分支) (#903) | 漏悬浮预览面、漏表格等构造、全局活动视图写错格、漏预览态分支 |
| 状态空间缺失 | #1034 #1019 #1055(焦点) | 不测重启、不测光标在隐藏区、不测动作后焦点 |
| 既有缺陷 | #1012 (#1016 #903) | md-bundle 移植带入 |

13 张重做中纯逻辑写错仅 1 张（#1012 输入配对）。**缺陷主体是验证设计与对齐缺失，不是编码能力。** 措施总账见文末附录。

## 二、对账表（强制）

batch 级反馈（多条一起提）与命中触发信号的单条新需求/优化，在拆票前必须产出一张对账表：

| #   | 用户原话       | agent 理解（行为化复述）        |  歧义点/候选（★=默认）   | 处置          |
| --- | ---------- | ---------------------- | :-------------: | ----------- |
| 1   | 页签间距加宽一个指针 | 16→32px                | ★+16px（另一解 ×2）  | 做票          |
| 2   | 徽标显示回车     | 回车图标（svg + aria-label） | ★图标（另一解：文字「回车」） | 做票          |
| 3   | （信息不足的条目）  | ——                     |    需要截图才能定验收    | **待补充**     |
| 4   | （与现行规格冲突）  | ——                     |  建议走 Δ-change   | **暂缓 + 理由** |
|     |            |                        |                 |             |

**固化位置**：整表作为 spec issue 的一条评论发布，标题固定为 `## 输入对账`，表头固定五列且顺序不变（`# | 用户原话 | agent 理解（行为化复述） | 歧义点/候选（★=默认） | 处置`）；表尾写一行用户确认：`确认：全按默认，#2 选 B`。C11 按此结构机检：段存在、五列、处置列非空且无 `待确认`、暂缓须带理由、有 `确认：` 行（只查结构，不判语义）。

### 触发与豁免（2026-11-22 扩至新需求/优化线）

**必须对账**：

- batch：≥2 条一起提（沿用原规则）。
- 单条新需求/优化，命中任一信号：形态/交互模型未定（面板结构、单双控件、出现时机）；新增用户可见面；无一手原型且无规范锚点；含判断词（「最方便 / 好看 / 舒服 / 差不多」）；跨面组合改动（一个需求同时改编辑面与外壳）。

**可豁免**（在 spec issue 留一行 `输入对账豁免: <理由>`，C11 认这一行）：

- `no-ui-impact` 的纯重构 / 纯文档 / 纯基建；
- 输入是逐字一手规格（规范条款、设计稿、用户已逐条给出验收标准），且不含判断词、无形态未定；
- 缺陷条目（缺陷线由 triage 证据复现兜底，走 DQ-1..DQ-3，不走对账）。

**未确认不拆票**：处置列写 `待确认` 即未完成对账；允许出 proposal/design/tasks 草稿，禁止拆票与实施（与 §七「未确认不实施」同一纪律）。

三条硬规则（裁定 2026-11-18）：

1. **强制**：batch 级反馈与命中触发信号的单条需求/优化，未经对账确认不得拆票。未命中信号的单条小缺陷可并入下一批对账，不强制单独一轮。
2. **禁止静默丢弃**：每一条编号反馈必须出现在表里；不做/暂缓必须写理由。处置列是用户核查漏网的唯一入口。
3. **回复约定**：候选全部带默认；用户回复「全按默认，#N 选 B，#M 补充：……」即完成一轮，成本一句话。

歧义候选给 2–3 个并标默认；交互形态争议（图标样式/面板结构/时机）出对比稿再裁，不靠文字猜。确认后 G0-PRE 把对账表固化进 spec issue；OQ（Open Questions）只留真开放问题。

## 三、何时用 /grill-me（升级路径，默认不用）

- **默认不用**：对账表的瓶颈是用户时间；grill-me 多轮追问把负担翻回用户，与回复约定相反。要治的病是「静默误读」，解药是复述+候选+处置列，不是加大提问量。
- **升级条件**：开放型新需求（非缺陷/优化），2–3 个候选形不成收敛（形态/交互模型未定，如「datetime 单面板」的面板结构）→ 限**一次 3–5 问**的 grill 轮把缺的决策问出来，随后回对账表。
- **缺陷不做 grill**：triage 走证据复现，不走访谈。
- 用户主动说「grill 我」随时触发（该 skill 自带触发词）。

## 四、一起提还是分开提（归并规则）

**按条目组织，不按消息组织。**

- 一条消息混需求/优化/缺陷：可以且推荐。同模块的一起提共享上下文、对账一次成表，避免顺序歧义（后面的缺陷被当成前面需求的修正）。
- 每条**编号并标类别**（缺陷/优化/需求）。类别标错没关系，对账表会纠正路由：需求/优化 → change 线（规格增量）；缺陷 → 缺陷线（triage→红→修）。
- 不同模块混一条消息也可以，按条目归并。
- **唯一必须立即单独提的：阻断性缺陷**（核心流程坏、阻塞继续测试），不等凑批。
- 频率：攒自然批次（测完一轮）最好，不一条一条发。（夜间节奏与验收点安排见 §七）

## 五、写法指南（怎么写 agent 理解得更准）

先兜底：**允许糙写**，对齐轮就是为糙输入设计的——写得糙没关系，跳过对齐轮才有风险。以下规律来自本轮真实票：

| 表述方式 | agent 容易偏到哪 | 建议写法 |
|---|---|---|
| 只说不要什么：「不要省略号」 | 解法空间大（缩小/换行/滚动/全显），默认常不中 | **正向描述终态**：「名称完整显示，放不下时页签条横向滚动」 |
| 引号内的词被当字面量：「徽标『回车』」 | 做成两个字的文本，用户要的是图标 | 要图标写「图标」；要文字才加引号 |
| 时机+位置混一句：「落点跟随显示」 | 各答对一半 | **拆开**：何时出现 / 出现在哪 / 何时消失 |
| 判断词：「最方便」「好看」「舒服」 | 无法换算成实现 | 给参照物：「像系统日历那样」「上一版那样」——参照 > 形容词 |
| 比喻单位：「加宽一个指针」 | 需换算回读确认 | 有数给数（「再宽 16px」），没有就等换算确认 |
| 一段塞多件事 | 漏接 | 一行一条、编号、标类别 |
| 总结式缺陷报告：「都没有实现」 | 只能按代码面盲查 | **三要素**：现象（+截图最好）/ 期望 / 复现路径 |
| 同音口误：「不要行号显示」 | 猜+确认（本轮猜对） | 关键名词写完扫一眼 |

- **截图是最高带宽的输入**：现象一眼定位到面。
- 引用界面元素用可见名字（「顶栏右侧的 ×」），不必学开发术语。
- 轻量模板（可抄，不强制——对账表会补缺口）：

```
[缺陷/优化/需求] 一句话标题
现象：…（截图更好）
期望：…（何时/何地/什么内容）
路径：…（缺陷必填）
```

## 六、与既有流程的衔接

- **G0-PRE 1a**：对账表（或 `输入对账豁免: <理由>` 一行）固化进 spec issue 的 `## 输入对账` 评论；C11 机检结构，不合格不得进入 1b/阶段二；用户反馈与锚点冲突时走 Δ-change（DQ-9 反模式）。
- **视觉类反馈**：四要素与候选终态见 [ui-feedback.md](./ui-feedback.md)；对账表负责覆盖与复述，四要素负责候选的具体化。
- **缺陷线**：triage / DQ-1..DQ-9 见 [defect-workflow.md](./defect-workflow.md)。
- **验证侧**：断言审计与反事实复跑见 [quality-gates.md](./quality-gates.md) QG-10；真机偏差分级见 DQ-9。

## 七、夜跑晨验节奏（2026-11-18 裁定）

用户晚间提交、夜里由 agent 跑批、白天验收——验收点从「每批一次」收敛到「每早一次」，夜里连续跑，不停等验收。

- **每晚总量 ≤8 票**：＝一个上午能实测的量；超出的票排次晚（已对账、已入看板，不会丢）。
- **实施顺序 = 语义风险倒序**：最新颖/最依赖用户裁定的票先做（校准样本），低风险缺陷修复随后。晨验先验前几票，发现理解偏差后，未开工的票按修正后的理解继续——拦住未实施的比重做已实施的便宜。
- **未确认不实施**：对账表未经用户确认的票，夜里降级为「诊断之夜」——只做 triage（复现/根因/红证据/triage brief 贴票），不写实现；用户晨间确认后次晚实施。
- **晨报验收卡**（每早一份）：本晚交付清单（功能语言）+ 每票待验收项（**直接引用 §九 交付对账表的行，不另写一套功能描述**）+ 截图证据 + 「建议优先实测」标注（语义风险高的票）。
- 配套纪律不变：全量对账不丢弃、全量拆票入库、每票独立 PR 可回退、重做走前置修正票；DQ-9/QG-10 门禁不放松。
- 节奏跟随提交与确认时间，不强制白天/夜晚；白天提交且确认后同样即时实施。

## 八、阶段进度汇报（不是交付对账）

拆票、落制品这类**没有代码合并**的阶段也要报进度，但它不是交付对账：一个功能点都没有，硬套 §九 的表就是用空表冒充交付——用户按表实测，只能点到「PR #1567 合并」这种没法点的行。

阶段汇报用独立格式，表头固定三列：

| 阶段        | 完成动作                    | 产出物编号   |
| ----------- | --------------------------- | ------------ |
| G0 拆票     | 需求拆为 8 张可开工票        | #1559–#1566  |
| G0 规划制品 | proposal / design / tasks / specs delta 落库 | PR #1567 |

约束（C12 机检，见 §九）：

- **表头不得含「交付功能点」「验法」「验收」字样**——出现即视为冒充交付对账表，拒收。
- 反过来，§九 交付对账表**只在有代码合并后出**；一个功能点都没有就不许出那张表。
- 产出物编号列写 issue / PR 号是本分（进度就是这个），不算缺陷；管制的是「把它写进交付功能点列」（§九 机检）。

## 九、交付对账表（开发后，逐条写明做了什么）

输入对账管「拆票前理解对不对」，交付对账管「交到手上的到底是对账里那条，还是别的」。缺了它，用户只能拿着一批 PR 标题和代码自己猜有哪些功能点可测——实测口径靠猜，就会出现「交付的功能与需求对账不一致」而当场发现不了。

**产出时机与位置（三层，缺一不算交付）**：

1. **每次交付即报（不等用户问）**：本票 / 本批合并后，在**回合回复里直接列出功能点清单**（就是下表，编号 + 功能模块 + 交付功能点 + 状态）——用户拿到就能逐条实测。同一批多票可在回合末合成一张表；只贴 PR 链接或文件路径不算报过。
2. **回填留档（G3）**：把同样内容写进 spec issue 的 `## 交付对账` 评论，逐票追加本票那几行。
3. **定稿（G4）**：change 全部票合并后、**关闭 spec issue 之前**行数与状态齐全，作为该评论的终版。

| #   | 功能模块 | 交付功能点（新增 / 调整 / 优化）                                                    | 状态                                |
| --- | -------- | ----------------------------------------------------------------------------------- | ----------------------------------- |
| 1   | 页签条   | 页签宽度改为弹性等比收缩，窗格变小时不再裁切标题（改前：固定宽度被覆盖）              | 已交付                              |
| 2   | 信息窗   | 「复制路径 / 复制文件」图标右移到最近保存时间行；成功提示改为悬浮 toast，1.4 秒后消失 | 已交付                              |
| 3   | 徽标     | ——                                                                                  | 未交付（暂缓：等下一轮对账定形态）  |
| 4   | 设置面板 | 字体候选列表改为中文名优先排序（切换字体时列表顺序变了）                            | 超出对账（请裁决：保留还是退票）    |

规则：

- **`#` 与「功能模块」沿用同一次 `## 输入对账` 的编号**，逐条对齐——这是发现「做偏了」的唯一机制。实施中冒出的新条目在本表续接编号，并在模块名后标 `新增`。
- **「交付功能点」写用户能测的行为**：能做什么、看到什么变化（改前 → 改后）。禁止写文件名、函数名、变量名、PR 号——那不是验收语言。
- **状态三选一**：`已交付` ／ `未交付（理由）` ／ `超出对账（请裁决）`。`未交付` 无理由视为未收口；`超出对账` 必须单列，不许并进已交付的行。
- **表尾留一行用户确认**：`确认：1、2 通过，4 保留`。与 §二 同一套回复约定。
- **禁止这样写**（上面示例第 4 行的正确形态是行为描述，不是模块名）：
  - `重构 tabStore` —— 模块名，用户没法测。
  - `PR #1567 合并` —— PR 号不是验收语言。
  - `已交付` —— 状态填进功能点列＝这一行没有任何可测内容。

**表头与状态机检（C12，G4 出口跑）**：`./scripts/cw-tickets-check.sh --change <名> --live`

- 表头必须精确四列（`#` / 功能模块 / 交付功能点… / 状态）；缺 `#` 列或表头换成别的名字 = 疑似阶段进度汇报冒充，拒收。
- 状态只认三值：`已交付` ／ `未交付（理由）` ／ `超出对账（请裁决）`；无理由的 `未交付`、其他措辞一律红。
- 「交付功能点」列命中 `PR ?#\d+` ／ `#\d{3,}` ／ `.ts(x)?` ／ `.rs` ／ `--strict` ／ `机检` ／ `看板` 任一 → 判不合格：那是引用，不是验收语言。
- 机检只管结构与形态，不管语义覆盖（那只能人读判，机器判语义会造假红假绿）——与 C11 同一取舍。

**用途**：用户按行逐条实测；实测不通过按 DQ-9 分级处理，需求本身变了则走 Δ-change。**没在回复里报出的功能点 = 用户不知道能测什么，等同没交付。**
